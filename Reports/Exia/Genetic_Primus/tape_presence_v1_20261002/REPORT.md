# Доступность tape для проверки исполнений замороженной модели

Проверка только локальных файлов; без сети, нового PnL, переобучения, validation labels и торгового runtime. Источник решений — неизменённый train-result линейной матрицы за июнь–июль 2026 года. Сопоставлены EMA (26 закрытых сделок) и 4-признаковый uniform (18), при исходном времени исполнения и задержке +1 четырёхчасовой бар. Оба half-life варианта и NoTrade не имеют исполнений.

Из frozen решений получено 52 перехода target у EMA и 36 у 4-признакового uniform. Для каждого перехода необходимы как минимум book ticker, L2 и trades по его инструменту/дате. Поскольку переходы без задержки стоят ровно в **00:00 UTC**, для as-of состояния перед границей необходим также файл **предыдущих UTC-суток**: файл текущих суток может начинаться уже после сигнала. После объединения одинаковых требований это **106 пар дата–инструмент × 3 потока = 318 уникальных суточных архивов**, охватывающих 24 даты от 2026-05-31 до 2026-07-25. Подробные имена перечислены в `result.json`; это необходимое условие покрытия, но ещё не гарантия непрерывного качественного стакана около каждой сделки.

В проверенном корне `C:\Users\anton\Downloads` обнаружены только четыре архива BTCUSDT: trades, incremental L2 и derivative ticker за 2024-12-01, book ticker за 2025-01-01. В `Retrodate` подходящих архивов по имени также не найдено. **Совпадений с 318 требуемыми именами — 0; execution_ready=false.** Прежняя отдельная проверка декабря (`recorded_archives_v1_20260914/REPORT.md`) действительно валидировала полное чтение трёх декабрьских архивов; текущий запуск прочитал у файлов лишь заголовок и первую запись, без повторной проверки CRC/EOF и внутрисуточной полноты.

Первый январский book-ticker event имеет exchange timestamp `2024-12-31 23:59:59.892 UTC`, но local receive timestamp `2025-01-01 00:00:00.445238 UTC`. Это подтверждает, почему нельзя ориентироваться только на дату биржевой метки в имени файла и почему для as-of у полуночи нужен соседний суточный раздел.

Даже получение всех 318 архивов не докажет fill по котировке: нужны проверки времён получения, свежести и целостности снимков, размеров заявок, spread, depth, очереди/проскальзывания и funding за удержание позиции. Старые BTC-файлы годятся для инженерных тестов парсера, **не** для калибровки исполнений восьми инструментов в 2026 году. Поскольку текущая модель уже проиграла NoTrade при идеализированном исполнении, массовую загрузку этих архивов для её «спасения» не рекомендую. Сначала требуется новая ограниченная гипотеза и независимые origin-кластеры; tape-запрос следует формировать под зарегистрированный следующий эксперимент.
