# Panteon Flash: описание проекта, Пантеона, игроков и агентов

Дата описания: 2026-05-21

Ветка разработки: `codex/Panteon_Flash`

Основные кодовые области:

- `src/panteon_v2/app/main_loop.py` - основной цикл принятия и исполнения решений.
- `src/panteon_v2/app/agent_bootstrap.py` - регистрация базовых, опциональных и экспериментальных агентов.
- `src/panteon_v2/selection/player.py` - протокол игрока и основные типы игроков.
- `src/panteon_v2/selection/voting.py` - политики ансамблевого голосования.
- `src/panteon_v2/selection/flash_allocator.py` - Flash-выбор лучшего актора по каждой криптовалюте.
- `src/panteon_v2/selection/strategist.py` - legacy-стратег глобального выбора игрока и shadow-оценки.
- `src/panteon_v2/selection/promotion_manifest.py` - правила допуска сигналов в реальную торговлю.
- `src/panteon_v2/domain/types.py` - базовые доменные типы: действия, режимы, сигналы, сделки и метрики.

## 1. Краткое резюме

`Panteon Flash` - новая упрощенная версия Пантеона для торговой системы криптовалют. Главная идея версии: убрать из production-пути слой глобального выбора игрока и заменить его прямым выбором лучшего доступного актора для каждой отдельной криптовалюты и торговой ситуации.

В старой схеме Пантеон выбирал одного лидера-игрока на весь рынок. Это усложняло отладку: хороший агент мог быть полезен на одной монете, но проигрывать как часть глобального игрока; плохое решение на одной паре могло маскироваться общей статистикой; ансамбли и одиночные агенты конкурировали через дополнительный слой абстракции.

В `Panteon Flash` логика проще:

1. Каждый агент или ансамблевый игрок формирует возможное действие.
2. Система оценивает кандидатов отдельно по каждой монете.
3. Для каждой монеты выбирается один лучший актор.
4. Игроки больше не являются обязательным уровнем выбора, но остаются ансамблевыми сущностями для статистики, визуализации и сравнения.
5. Если ни один кандидат не проходит фильтры качества, Пантеон выбирает `NoTrade`, то есть осознанное бездействие.

Целевая инженерная цель версии - сделать систему проще для эксплуатации, отладки, анализа причин убытков и постепенного улучшения агентов.

## 2. Что такое проект

Проект - это экспериментальная и production-ориентированная торговая платформа для криптовалют, построенная вокруг нескольких типов торговой логики:

- одиночные агенты, которые принимают решения по своим правилам;
- ансамблевые игроки, которые агрегируют мнения нескольких агентов;
- Пантеон, который выбирает, какому актору доверить конкретную ситуацию;
- shadow-контур, который проверяет новые идеи без прямого влияния на реальные сделки;
- память результатов, которая хранит статистику, атрибуцию и историю решений;
- отчеты и визуализации, которые помогают искать ошибки и улучшать модели.

Проект развивается в сторону модели, где прибыльность должна появляться не за счет случайного выбора лучшего агента на истории, а за счет контролируемого отбора устойчивых сигналов. Поэтому важна не только итоговая доходность, но и объяснимость: кто дал сигнал, почему он был выбран, какие фильтры сработали, какие кандидаты были отклонены и как это менялось во времени.

## 3. Доменные сущности

### 3.1. Режим рынка

Рыночный режим описывается enum `Regime`:

- `BULLISH` - бычий рынок или локальный бычий режим.
- `BEARISH` - медвежий режим.
- `NEUTRAL` - боковой или неопределенный режим.
- `CRASH` - резкий стрессовый режим, падение или паника.

Режим рынка важен для:

- выбора допустимых агентов;
- оценки качества сигналов;
- фильтрации экспериментальных вариаций;
- анализа того, где агент реально полезен.

Один и тот же агент может быть хорошим в `CRASH`, но вредным в `NEUTRAL`. Поэтому `Panteon Flash` не стремится найти одного универсального победителя, а выбирает по символу и ситуации.

### 3.2. Действия

Действия описываются enum `Action`:

- `HOLD` - ничего не делать.
- `SPOT_BUY_HALF` - купить половинный объем на споте.
- `SPOT_BUY_FULL` - купить полный объем на споте.
- `SPOT_SELL_ALL` - продать всю спотовую позицию.
- `FUT_LONG_HALF` - открыть половинный long на фьючерсах.
- `FUT_LONG_FULL` - открыть полный long на фьючерсах.
- `FUT_SHORT_HALF` - открыть половинный short на фьючерсах.
- `FUT_SHORT_FULL` - открыть полный short на фьючерсах.
- `FUT_CLOSE_ALL` - закрыть фьючерсную позицию.

У `Action` есть доменные признаки:

- `is_open` - действие открывает позицию.
- `is_close` - действие закрывает позицию.
- `is_long_open` - открытие long.
- `is_short_open` - открытие short.
- `side` - сторона сделки.
- `fraction` - доля объема.

Это позволяет строить фильтры не на строках, а на доменной семантике. Например, wrapper агента может разрешать только short-действия или только spot-действия.

### 3.3. Сигнал

Сигнал - это результат решения актора по конкретной монете. Важные поля сигнала:

- `id` - идентификатор сигнала.
- `symbol` - торговая пара, например `BTC/USDT`.
- `action` - действие из `Action`.
- `agent` или `actor` - источник решения.
- `features` - дополнительные признаки, объясняющие контекст.

В `Panteon Flash` особенно важен signal key:

```text
actor_key|SYMBOL|ACTION
```

Пример:

```text
agent:MomentumScalper|BTC/USDT|FUT_SHORT_FULL
```

Такой ключ позволяет оценивать не просто "агент хороший или плохой", а конкретную связку: источник сигнала, монета, действие. Это важная основа для дальнейшей прибыльности, потому что один агент может быть полезен только в узком наборе инструментов и действий.

## 4. Архитектура проекта

### 4.1. Слои системы

Система условно делится на несколько слоев:

1. Domain layer.
   Содержит базовые типы: действия, режимы, сигналы, позиции, сделки, метрики.

2. Agent layer.
   Содержит торговых агентов. Агент смотрит на `MarketSnapshot` и возвращает действия по символам.

3. Player layer.
   Содержит ансамблевые сущности. Игрок может объединять несколько агентов через voting policy. В `Panteon Flash` игроки не являются обязательным selection-слоем, но остаются важными statistical actors.

4. Decision layer.
   В legacy v2 это `Strategist`, выбирающий одного глобального игрока. В Flash это `FlashAllocator`, выбирающий лучшего актора отдельно по каждой монете.

5. Execution layer.
   Отвечает за превращение выбранных сигналов в сделки через risk limits, position tracking и exchange adapters.

6. Memory and attribution layer.
   Хранит статистику результатов, shadow-оценки, атрибуцию сигналов, события, карантины и degraded keys.

7. Reporting layer.
   Строит отчеты, визуализации и сравнительный анализ Пантеона, игроков, агентов и signal keys.

### 4.2. Single Source of Truth

Архитектурная цель v2 и Flash - уменьшить расхождения между разными источниками правды. Важные принципы:

- решения пишутся в event log;
- сделки и результаты атрибутируются к источникам сигналов;
- статистика строится из воспроизводимых событий;
- shadow-результаты отделены от real execution;
- selection audit сохраняет не только победителя, но и отклоненных кандидатов.

Это важно для отладки. Если сделка убыточна, нужно восстановить цепочку:

```text
market snapshot -> candidates -> filters -> selected actor -> signal -> execution -> trade result -> attribution
```

## 5. Пантеон

### 5.1. Роль Пантеона

Пантеон - это управляющий слой, который не обязан сам быть торговой стратегией. Его задача - выбрать, какой торговой логике доверять в текущей ситуации.

Пантеон должен быть прибыльнее своих составляющих за счет:

- выбора лучших signal keys вместо слепого доверия одному агенту;
- отказа от торговли, когда преимущество не доказано;
- отдельной оценки по символам;
- допуска новых идей через shadow и promotion manifest;
- ограничения концентрации в отдельных акторах;
- быстрой диагностики деградирующих сигналов.

### 5.2. Legacy Panteon v2

В классической v2-схеме существовал глобальный выбор игрока:

```text
players -> Strategist -> selected player -> signals -> execution
```

`Strategist` сравнивал игроков и выбирал одного лидера. Такой подход дает понятную архитектуру турнира игроков, но имеет проблемы:

- один глобальный лидер может быть хорош на `BTC`, но плох на `SOL`;
- ансамблевый игрок может скрывать вклад конкретного агента;
- сложно понять, какой именно signal key приносит прибыль;
- ухудшается диагностика, когда причина убытка находится внутри выбранного игрока;
- полезные агенты могут не попадать в execution, если их игрок не выбран глобально.

### 5.3. Panteon Flash

`Panteon Flash` меняет production-путь:

```text
agents + ensemble players -> FlashAllocator -> best actor per symbol -> execution
```

Главное отличие: выбор делается не один раз на весь рынок, а отдельно по каждой торговой паре.

Например:

- для `BTC/USDT` может быть выбран `Solo_MomentumScalper`;
- для `SOL/USDT` может быть выбран ансамблевый игрок `VolatilityBreakout_Weighted`;
- для `ETH/USDT` может быть выбран `NoTrade`;
- для `AVAX/USDT` может быть выбран экспериментальный wrapper, если он уже прошел promotion gates.

Такой дизайн лучше подходит для отладки и роста прибыльности, потому что каждая монета получает собственного победителя.

### 5.4. Что значит "игроки - ансамблевые сущности"

В `Panteon Flash` игрок больше не является обязательным уровнем production-выбора. Игрок теперь трактуется как ensemble actor:

- он может голосовать на основе нескольких агентов;
- он имеет собственную статистику;
- он попадает в визуализации;
- он может конкурировать с одиночными агентами;
- он может быть выбран для конкретной монеты, если его сигнал лучше альтернатив.

То есть игрок не исчезает. Удаляется именно слой "сначала выбрать игрока, потом исполнять только его".

## 6. Поток принятия решения в Panteon Flash

### 6.1. Общая схема

```text
MarketSnapshot
    -> real executable agents
    -> ensemble players
    -> solo candidate wrappers
    -> shadow statistics
    -> promotion manifest
    -> FlashAllocator.decide(...)
    -> one FlashDecision per symbol
    -> executable signals
    -> TradeExecutor
    -> EventLog and attribution
```

### 6.2. Подготовка кандидатов

Основной цикл в `src/panteon_v2/app/main_loop.py` строит набор кандидатов:

- реальные агенты из registry;
- ансамблевые игроки;
- fixed candidates;
- regime/profile candidates;
- rotating candidates;
- solo wrappers вида `Solo_<AgentLabel>`;
- fallback candidates из registry.

Для Flash важны только executable actors. Shadow-only агенты и агенты без признака `live_trading_eligible` не должны попадать напрямую в реальные сделки.

### 6.3. Shadow-контур

Shadow-контур нужен для проверки идей без реального исполнения. Он помогает:

- увидеть, как агент вел бы себя на текущем рынке;
- накопить статистику по новым wrapper-агентам;
- проверить signal key до допуска в production;
- сравнить одиночных агентов и ансамбли;
- выявить деградацию сигналов.

Важный принцип: экспериментальная идея сначала должна доказать полезность в shadow, а уже потом получить право на real allocation.

### 6.4. Promotion manifest

`promotion_manifest.py` строит список signal keys, которые разрешены к реальному использованию. Текущие базовые критерии:

- минимум закрытых сделок на полной истории;
- минимум недавних закрытых сделок;
- положительный PnL на полной истории;
- положительный недавний PnL;
- ограниченный max drawdown;
- достаточный win rate;
- отсутствие недавнего downside выше лимита.

Если signal key не проходит критерии, `FlashAllocator` может отклонить его с причиной `flash_signal_not_promoted`.

Это защищает систему от случайного добавления новых агентов в real trading без доказанной статистики.

### 6.5. FlashAllocator

`FlashAllocator` - центральный компонент `Panteon Flash`.

Он получает:

- рыночный snapshot;
- список агентов;
- список игроков;
- shadow confirmation statistics;
- degraded signal keys;
- promoted signal keys;
- настройки риск-фильтров и порогов.

На выходе он возвращает список `FlashDecision`, по одному решению на символ.

Каждое решение содержит:

- `symbol` - монета;
- `selected_actor` - выбранный актор;
- `actor_type` - тип актора, например `agent`, `ensemble`, `no_trade`;
- `score` - итоговая оценка;
- `action` - выбранное действие;
- `reason` - причина выбора;
- `signal` - исполняемый сигнал или `None`;
- `candidates` - audit всех кандидатов.

### 6.6. Почему audit кандидатов важен

`FlashCandidateAudit` сохраняет не только победителя, но и отклоненных кандидатов:

- кто был кандидатом;
- какой action он предлагал;
- какой score получил;
- какой rank занял;
- был ли отклонен;
- по какой причине отклонен;
- какие метрики были доступны;
- что показал shadow;
- какой был lookback return.

Это один из главных инструментов отладки. Он позволяет ответить на вопросы:

- почему Пантеон не открыл сделку;
- почему был выбран не самый очевидный агент;
- какой фильтр заблокировал сигнал;
- не слишком ли строгий promotion manifest;
- не слишком ли слабый score threshold;
- не доминирует ли один актор;
- какие агенты часто дают сигналы, но почти всегда отклоняются.

### 6.7. NoTrade как полноценное решение

`NoTradePlayer` возвращает пустой набор сигналов. В Flash он используется как явное решение:

```text
лучший результат для этой монеты сейчас - не торговать
```

Это принципиально важно. Система не должна открывать сделку только потому, что какой-то агент дал action. Если edge не доказан, бездействие может быть прибыльнее торговли.

## 7. Игроки

### 7.1. Что такое игрок

Игрок реализует протокол `Player`:

- `label` - имя игрока;
- `affinity` - предпочтения или специализация;
- `agent_labels` - агенты, из которых состоит игрок;
- `vote(market, signal_id_start)` - метод, возвращающий список сигналов.

В `Panteon Flash` игрок рассматривается как ансамблевый актор. Он может быть выбран по конкретному символу, но больше не является глобальным контейнером, который полностью определяет весь execution.

### 7.2. NoTradePlayer

`NoTradePlayer` - специальный игрок с `actor_type="no_trade"`.

Назначение:

- явно фиксировать отказ от торговли;
- участвовать в decision audit;
- отделять "нет сигнала" от "система сломалась";
- использовать бездействие как контрольную альтернативу.

### 7.3. EnsemblePlayer

`EnsemblePlayer` объединяет несколько агентов:

- вызывает `act(market)` у каждого агента;
- фильтрует некорректные символы и действия;
- передает голоса в voting policy;
- превращает агрегированное решение в `Signal`.

Тип игрока:

```text
actor_type="ensemble"
```

Игрок может использовать веса агентов и threshold profile. Это позволяет делать не простое большинство, а более гибкое согласование.

### 7.4. RotatingAgentPlayer

`RotatingAgentPlayer` - ансамблевый игрок, который выбирает одного агента из приоритетного списка, зависящего от режима рынка.

Назначение:

- переключаться между агентами по режиму;
- не смешивать конфликтующие сигналы;
- использовать первый пригодный actionable сигнал.

Такой игрок полезен, когда заранее известно, какие агенты лучше подходят для `BULLISH`, `BEARISH`, `NEUTRAL` или `CRASH`.

### 7.5. Solo wrappers

В Flash одиночные агенты могут быть обернуты как `Solo_<AgentLabel>`. Это нужно для:

- сравнения агента с ансамблями в едином формате;
- сохранения player-like статистики;
- участия одиночных агентов в Flash allocation;
- совместимости с отчетами и legacy-инфраструктурой.

Пример:

```text
MomentumScalper -> Solo_MomentumScalper
```

### 7.6. Политики голосования игроков

#### WeightedConsensus

`WeightedConsensus` агрегирует направления с учетом весов:

- long open дает положительный directional vote;
- short open дает отрицательный directional vote;
- close идет отдельным каналом;
- при достаточной силе открывает full или half действие;
- при достаточном close consensus возвращает `FUT_CLOSE_ALL`.

Эта политика подходит для ансамблей, где несколько агентов могут иметь разную силу доверия.

#### StrongConsensus

`StrongConsensus` требует более жесткого согласия:

- open допускается только если активные агенты согласны по направлению;
- close допускается, если есть close vote.

Эта политика снижает частоту сделок и может быть полезна для уменьшения шума.

#### RiskParity

`RiskParity` стремится учитывать риск и волатильность. Идея - не давать слишком большой вес источникам, которые создают непропорциональную риск-концентрацию.

### 7.7. ThresholdProfile

`ThresholdProfile` задает пороги открытия и закрытия:

- `open_single`;
- `open_multi`;
- `open_floor`;
- `close_single`;
- `close_multi`;
- `close_strong`;
- noise-related bonuses.

Пороговый профиль позволяет регулировать агрессивность ансамбля без переписывания самих агентов.

## 8. Агенты

### 8.1. Что такое агент

Агент - это торговая логика с интерфейсом:

```text
act(market) -> dict[symbol, Action]
```

Агент не обязан знать о Пантеоне. Он смотрит на рынок и предлагает действие. Пантеон уже решает, можно ли этому действию доверять.

Ключевые свойства хорошего агента:

- понятная специализация;
- стабильная статистика по signal keys;
- предсказуемое поведение в разных режимах;
- ограниченная зона применения;
- диагностируемые причины ошибок.

### 8.2. Базовые агенты

В `agent_bootstrap.py` зарегистрирован набор известных v1-агентов. Их можно разделить на несколько семейств.

| Агент | Ориентировочная роль |
| --- | --- |
| `FundingArb` | Использует funding/derivatives bias и арбитражные перекосы. |
| `MomentumScalper` | Краткосрочный momentum/scalping. |
| `LiveAfterShock` | Поведение после резкого движения, post-shock continuation или rebound. |
| `LiveCrashHunter` | Поиск crash/downside ситуаций. |
| `LiveRegimePullback` | Pullback-логика с учетом режима рынка. |
| `LiveMeanRev` | Mean reversion после отклонений. |
| `LiveTrendFollow` | Следование тренду. |
| `LiveVolCompress` | Ситуации сжатия волатильности перед движением. |
| `RichardDennis` | Turtle/trend breakout стиль. |
| `LiveOIBreakout` | Breakout по open interest или похожим признакам. |
| `ResearchValidatorAgent` | Валидационный или исследовательский сигнал. |
| `VolBreakoutHunter` | Поиск volatility breakout. |
| `BullRotationAgent` | Ротация активов в бычьем режиме. |
| `BearReliefFadeAgent` | Fade relief rally в медвежьем режиме. |
| `NeutralRangeScalper` | Scalping внутри нейтрального диапазона. |
| `NeutralLiquiditySweep` | Работа с liquidity sweep в range/neutral условиях. |
| `AnchorFlowMomentum` | Momentum от anchor flow или устойчивого потока. |
| `CrashPanicShortAgent` | Short-логика для panic/crash режима. |
| `PlayerFunding` | Funding-ориентированный player-style источник. |

Точные правила каждого агента нужно смотреть в его реализации, но для уровня Пантеона важно не внутреннее описание, а статистика его signal keys.

### 8.3. Опциональные genetics-агенты

Опциональные агенты:

- `GeneticsGenomeEnsemble`;
- `GeneticsCore`;
- `GeneticsBullish`;
- `GeneticsBearish`;
- `GeneticsNeutral`;
- `GeneticsRegimeRouter`.

Они подключаются отдельно, например через `PANTEON_V2_LOAD_GENETICS=1` или явную конфигурацию. Их стоит держать под особенно строгим shadow-контролем, потому что такие модели легко переобучить на истории.

### 8.4. Экспериментальные Flash-вариации

`ActionFilterAgent` позволяет создавать wrapper-версии существующих агентов:

- разрешить только определенные actions;
- разрешить только определенные symbols;
- запретить отдельные symbols;
- разрешить только отдельные regimes;
- сохранить исходного агента как base, но ограничить область применения.

Экспериментальные specs:

| Wrapper | Базовый агент | Идея |
| --- | --- | --- |
| `MomentumScalperShortOnly` | `MomentumScalper` | Разрешить только short и close действия. |
| `MomentumScalperSpotQuality` | `MomentumScalper` | Использовать spot-действия только на выбранных quality symbols. |
| `VolBreakoutSpotOnly` | `VolBreakoutHunter` | Проверить volatility breakout только в spot-режиме. |
| `MomentumScalperShortCrashOnly` | `MomentumScalper` | Проверить short-логику только в `CRASH`. |
| `MomentumScalperShortBearOnly` | `MomentumScalper` | Проверить short-логику только в `BEARISH`. |
| `MomentumScalperSpotPullbackOnly` | `MomentumScalper` | Проверить spot pullback в `NEUTRAL` и `BULLISH`. |
| `ResearchValidatorNeutralOnly` | `ResearchValidatorAgent` | Ограничить research validation нейтральным режимом. |
| `FundingArbBearOnly` | `FundingArb` | Проверить funding-логику только в медвежьем режиме. |
| `CrashPanicCrashOnly` | `CrashPanicShortAgent` | Оставить crash panic short только в `CRASH`. |

Это хороший путь для дальнейшего роста прибыльности: вместо добавления полностью новых сложных агентов можно сначала проверить более узкие специализации уже существующих.

## 9. Как Пантеон выбирает лучшего актора

### 9.1. Кандидаты

Кандидатом может быть:

- одиночный агент;
- solo wrapper;
- ensemble player;
- rotating player;
- fixed/profile player;
- `NoTrade`.

Каждый кандидат оценивается по конкретному символу. Это ключевое отличие от глобального выбора игрока.

### 9.2. Фильтры допуска

`FlashAllocator` может отклонить кандидата по нескольким причинам:

- актор в карантине;
- нет действия;
- символ не совпадает с текущим decision symbol;
- недостаточно закрытых сделок;
- PnL ниже минимального порога;
- shadow confirmation недостаточен;
- signal key деградировал;
- signal key запрещен deny-list;
- signal key не прошел promotion manifest;
- score ниже `min_score_to_trade`;
- есть overextension guard;
- превышен cap по сигналам одного актора.

Каждая причина должна быть видна в audit. Это делает систему пригодной для диагностики.

### 9.3. Score

Score - итоговая оценка кандидата. Она может учитывать:

- историческую эффективность;
- recent performance;
- shadow confirmation;
- actionable bonus;
- качество метрик;
- режим рынка;
- degraded status;
- дополнительные ограничения конфигурации.

Цель score - не создать идеальную математическую оценку, а дать воспроизводимый ранжирующий механизм, который можно анализировать и улучшать.

### 9.4. Actor caps

Ограничение `max_signals_per_actor` защищает от ситуации, когда один актор захватывает слишком много решений. Это важно, потому что даже прибыльный агент может стать источником скрытой корреляции и просадки.

Для promoted actors возможны отдельные cap overrides. Это поддерживает принцип earned concentration: актор может получить больше места только после доказанной эффективности.

## 10. Отладка и анализ

### 10.1. Что нужно смотреть в первую очередь

Для поиска ошибок и улучшения моделей важны не только equity curve и итоговый PnL. Нужно анализировать:

- `FlashDecision` по каждому символу;
- audit отклоненных кандидатов;
- signal keys;
- PnL по agent;
- PnL по player;
- PnL по symbol;
- PnL по regime;
- PnL по action;
- PnL по direction;
- NoTrade opportunities;
- shadow-vs-real расхождение;
- degradation events;
- promotion manifest rejects;
- концентрацию решений по акторам.

### 10.2. Главные вопросы для диагностики

1. Пантеон действительно выбирает лучшего кандидата или просто самого активного?
2. Какие signal keys стабильно зарабатывают?
3. Какие signal keys дают много сделок, но портят результат?
4. Какие агенты хороши только в одном режиме?
5. Какие монеты системно убыточны для большинства агентов?
6. Не слишком ли часто `NoTrade` блокирует прибыльные сделки?
7. Не слишком ли слабо `NoTrade` блокирует убыточные сделки?
8. Есть ли агенты, которые полезны только как часть ансамбля?
9. Есть ли ансамбли, которые хуже своих лучших участников?
10. Пантеон прибыльнее лучших составляющих на out-of-sample периодах?

### 10.3. Минимальный набор отчетов

Для дальнейшей работы стоит поддерживать такие отчеты:

- equity curve Пантеона;
- equity curve каждого агента;
- equity curve каждого игрока;
- comparison: Panteon Flash vs best standalone;
- signal-key leaderboard;
- rejected candidates report;
- promotion manifest report;
- regime breakdown;
- symbol breakdown;
- action breakdown;
- drawdown report;
- monthly returns heatmap;
- live-vs-shadow divergence.

## 11. Реальная торговля

### 11.1. Можно ли начинать реальные торги

Сам факт наличия `Panteon Flash` не означает готовность к реальным торгам. Реальные торги можно рассматривать только после прохождения следующих условий:

- 5-летний backtest не содержит очевидных аномалий и survivorship/leakage ошибок;
- отдельный 1-летний или 6-месячный sanity run не показывает деградацию;
- Пантеон стабильно лучше лучших одиночных составляющих на out-of-sample;
- результаты не зависят от одной монеты или одного периода;
- есть отрицательные тесты, где система корректно выбирает `NoTrade`;
- все real-trading signal keys прошли promotion manifest;
- экспериментальные wrapper-агенты не попадают в real execution без допуска;
- есть мониторинг live расхождения;
- есть kill switch и лимиты риска;
- execution layer протестирован отдельно от strategy layer.

До выполнения этих условий корректный статус - research/shadow или paper trading, а не полноценная real-money эксплуатация.

### 11.2. Почему Пантеон должен быть лучше составляющих

Пантеон имеет смысл только если он добавляет value поверх агентов. Он должен выигрывать за счет:

- отбора лучшего актора по символу;
- фильтрации плохих signal keys;
- режима `NoTrade`;
- контроля деградации;
- ограничения концентрации;
- быстрого отключения убыточных связок;
- допуска новых идей только через статистическое подтверждение.

Если Пантеон не обгоняет лучший standalone agent/player, значит selection layer добавляет шум или слишком поздно реагирует на качество сигналов.

## 12. Стратегия дальнейшего улучшения

### 12.1. Улучшать не "агентов вообще", а signal keys

Самая перспективная единица анализа:

```text
actor_key + symbol + action + regime
```

Именно здесь чаще всего находится edge. Например:

- агент может быть плох в среднем, но хорош на `BTC/USDT` short в `CRASH`;
- ensemble может быть хорош только на high-liquidity symbols;
- spot-версия агента может быть стабильнее futures-версии;
- close-сигналы могут быть полезнее open-сигналов.

### 12.2. Расширять через controlled variants

Новые агенты лучше добавлять не сразу как production actors, а как controlled variants:

- ограничить symbols;
- ограничить actions;
- ограничить regimes;
- отправить в shadow;
- накопить signal-key статистику;
- только потом допускать через promotion manifest.

Такой подход проще отлаживать, чем добавлять большой универсальный агент.

### 12.3. Улучшать NoTrade

`NoTrade` должен быть не пассивным fallback, а активной частью profitability strategy. Нужно измерять:

- сколько убыточных сделок он предотвратил;
- сколько прибыльных сделок он пропустил;
- какие фильтры чаще всего приводят к `NoTrade`;
- где thresholds слишком строгие;
- где thresholds слишком слабые.

### 12.4. Сравнивать с компонентами

Каждый прогон должен отвечать на вопрос:

```text
Panteon Flash > best standalone agent/player?
```

Если нет, нужно смотреть:

- проигрыш из-за late switching;
- проигрыш из-за неправильного score;
- проигрыш из-за caps;
- проигрыш из-за promotion gates;
- проигрыш из-за over-filtering;
- проигрыш из-за выбора ансамбля хуже одиночного агента.

### 12.5. Расширить тесты

Рекомендуемые тестовые направления:

- короткий smoke backtest на 3-6 месяцев для быстрого выявления поломок;
- 1-летний regression backtest перед длинным прогоном;
- 5-летний full backtest для устойчивости;
- walk-forward matrix;
- symbol holdout;
- regime holdout;
- fee/slippage stress;
- latency/execution stress;
- crash-only tests;
- NoTrade counterfactual tests;
- shadow-to-real promotion tests;
- deterministic replay of one bad trade.

## 13. Глоссарий

| Термин | Значение |
| --- | --- |
| Пантеон | Управляющий слой, выбирающий, кому доверить торговое решение. |
| Panteon Flash | Версия Пантеона с per-symbol выбором лучшего актора. |
| Агент | Одиночная торговая логика, возвращающая действия по рынку. |
| Игрок | Ансамблевая сущность, агрегирующая агентов. |
| Актор | Общее имя для агента, игрока, solo wrapper или NoTrade. |
| Signal key | Уникальная связка actor, symbol и action. |
| Shadow | Контур тестирования без реального исполнения. |
| Promotion manifest | Список signal keys, допущенных к real execution. |
| NoTrade | Осознанное решение не торговать. |
| FlashDecision | Итоговое решение FlashAllocator по одному символу. |
| FlashCandidateAudit | Диагностическая запись по кандидату и причине выбора или отклонения. |

## 14. Итоговое описание одной фразой

`Panteon Flash` - это упрощенный, более диагностируемый Пантеон, который убирает глобальный слой выбора игрока, рассматривает игроков как ансамблевых statistical actors и выбирает одного лучшего агента или игрока для каждой криптовалюты отдельно, используя shadow-статистику, promotion gates, degradation guards, caps и audit причин выбора.
